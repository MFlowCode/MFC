    How a cluster test job fails

    A test job on a cluster checks out the code on a runner on the login node, builds MFC in a SLURM job, runs the test cases in SLURM jobs against that build, and uploads its logs. It can go red at any of those steps. The columns of the first table above are these causes.

    CauseWhat happenedWhose problemWhat to do
    TestsOne or more test cases failed after three attempts, or so many failed that the run stopped early because the build or environment looked broken.Usually the change. One compiler or offload model only: that lane.Look the case up in the table above. Failing on every lane: fix the change. One lane only: compare with that lane on master.
    BuildMFC did not compile, twice. The second attempt starts from a cleared build directory. The change, if other lanes built it; otherwise that compiler or its modules.Read the build log in the job.
    Cluster downThe cluster's partitions were not accepting jobs when the lane started. The cluster.Nothing: it is re-run automatically after a wait.
    Never startedThe SLURM job waited in the queue past CI's limit (3 h) and was withdrawn so it would not hold a runner. The queue: too many jobs for the nodes CI may use.Nothing: it is re-run automatically after a wait. If it is frequent, CI is asking for more than the cluster gives it.
    SLURM time limitThe SLURM job reached its time limit (1 h 59 min on Frontier, 3 h for tests on Phoenix) before finishing. Usually the machine: a slow node or GPU model, or a filesystem stall.Re-run. If it repeats on one lane, the suite no longer fits there.
    Bad nodeA check run on the compute node before the tests found it unusable (for example a GPU that will not initialize). CI excludes that node and tries one other; this is the second one failing too.The cluster. Re-run later; report the node if it keeps appearing.
    Git checkoutThe runner could not check out the code, before anything was built or run. The runner's workspace or the cluster's filesystem.Re-run. Nothing was tested.
    Artifact uploadThe job's work was done; uploading its logs to GitHub failed.GitHub or the network. Read the job's own output for the test result; re-run if a green check is needed.
    RunnerThe runner process was stopped, lost its filesystem, or a setup step ran past its limit. The runner or the cluster.Re-run.
    OtherNone of the above was recognized in the log.Unknown.Read the job.

    Two outcomes are not failures. Cancelled means a newer commit arrived and replaced the run. Passed on a retry means a case failed and then passed within its three attempts; the job is green, and the case is counted above with ↻ because a case that often needs a retry is unreliable on that lane.

    How a test case fails

    The "usual error" column is one of the test runner's own classes.

    ErrorWhat it meansCan a retry fix it
    Tolerance mismatchThe case ran, and its output differs from the stored reference by more than the tolerance. Differences near round-off on a single compiler usually mean that compiler orders the arithmetic differently. No: the same binary on the same input gives the same numbers.
    Execution failedA program did not start or exited with an error.Sometimes: it can be the launcher or the node.
    GPU memory faultThe program faulted in GPU memory.No.
    TimeoutThe case ran past the per-case time limit, usually a hang.Sometimes.
    NaN detectedThe solution became not-a-number.No.
